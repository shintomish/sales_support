# スコア計算ロジック説明資料 (営業協議用)

**作成日**: 2026-05-21 / **最終更新**: 2026-05-30
**目的**: 営業部との協議のため、現行システムが算出する各スコアの意味と計算方法を整理する
**対象**: 営業担当 / 開発側 / 管理者

---

## 0.1 2026-05-26 営業部協議反映分（更新ノート）

- **情報不足 / 不明項目を 1 点に減点**（中間点撤廃）。対象: 勤務形態 5→1 / 勤務地 2→1 / 契約 3→1 / 稼働不明 3→1 / 過去取引不明 2→1。当初「0 点化」案だったが、情報の薄い技術者メールが閾値 70 に届かず候補ゼロ件になることが実測で判明し、営業判断で **0→1 点に緩和**。
- **年齢上限 +2 歳まで許容**: 即除外せず **7 点**で候補に残す。+3 歳以降は従来通り除外。国籍不適合は即 0 点維持。
- **鮮度マッチング画面（[`docs/470_fresh_mail_matching.md`](470_fresh_mail_matching.md)）の表示閾値デフォルトを「高(70)→中(60)」に変更**。1 点化でスコアが下がり 70 が空になるため。実測で 8〜20 件と健全。
- **管理者限定ボタン化**: `/engineer-mails`・`/project-mails` の「全件再スコア」「情報抽出」を `tenant_admin` / `super_admin` のみ表示（営業 `tenant_user` には非表示）。
- **ドメイン信頼度補正の毎晩自動反映**: 毎晩 02:40 JST に from_address ドメイン補正の差分のみ再計算（`refresh-domain-bonus` Schedule、本番限定）。「全件再スコア」ボタンの代替。

## 0. はじめに — スコアは 2 種類ある

システム内には **役割の異なる 2 種類のスコア** が存在します。混同を避けるため、まず全体像を整理します。

| スコア種別 | 何を測るか | 算出タイミング | 算出場所 | 表示先 |
|---|---|---|---|---|
| **① 品質スコア** | メール 1 通から **どれだけ有用な情報が抽出できたか** | メール取込時 (15分毎の同期で自動) | `ProjectMailScoringService` / `EngineerMailScoringService` | `/matching` `/engineer-mails` 一覧の「スコア」列 |
| **② マッチスコア** | **案件 × 技術者の相性** を 0〜100 で評価 | 画面表示時にリアルタイム計算 | `ProjectMailMatchingService::score()` | マッチ候補カードの大きな数字 (例: ◎ 82) |

### イメージ図
```
[メール取込]
   ├─ 案件メール   → 品質スコア 0〜85 → ステータス分類 (§1.3 参照)
   └─ 技術者メール → 品質スコア 0〜70 → ステータス分類 (§1.3 参照)

[画面で案件 vs 技術者を表示]
   └─ 該当ペアに対してマッチスコア 0〜100 を計算 (◎/○/△ ラベル付き)
```

> ステータスは **案件メール (PMS = `project_mail_sources`) と技術者メール (EMS = `engineer_mail_sources`) の各 `status` カラム** に記録されます。閾値ごとの詳細は §1.3。

## 1. 品質スコア (メール抽出時の評価)

メール本文に「単価いくら、勤務地どこ、技術スタック何々」のような情報が**どれだけ書かれているか**を点数化したものです。**情報量の指標**であり、案件として良い・悪いを判定するものではありません。

### 1.1 案件メール (PMS) の品質スコア [上限 85 点]

| 項目 | 加点 | 検出キーワードの例 |
|---|---|---|
| 案件確度A | **+15** | 「案件」「募集」「ご紹介」「お引き合い」など (明示的な案件紹介ワード) |
| 案件確度B | **+10** | 「以下」「下記」「条件」「以下に」など (条件提示ワード) |
| 技術スタック (言語) | 1個目 **+10** / 2個目 **+5** | Java, Python, JavaScript, PHP, Go, TypeScript, Ruby など |
| 技術スタック (インフラ) | **+5** | AWS, Azure, GCP, Docker, Kubernetes など |
| 技術スタック (DB) | **+3** | Oracle, MySQL, PostgreSQL, MongoDB など |
| 単価具体性 | **+15** | 「80万」「100万円」など具体的な数値 (`XX万` 記載) |
| 勤務地 | **+10** | 「東京」「リモート」「在宅」「常駐」など |
| 工程 (基本設計クラス) | **+10** | 「基本設計」「詳細設計」「要件定義」など |
| 工程 (開発クラス) | **+7** | 「開発」「実装」「コーディング」など |
| 工程 (その他) | **+4** | 「テスト」「保守」「運用」など |
| 稼働期間 | **+5** | 「即日」「長期」「人月」などタイミング表現 |
| **ペナルティ: 単価曖昧** | **-10** | 「単価応相談」「経験により」「スキル見合い」 |
| **ペナルティ: 高次商流** | **-10** | 「弊社1次」「上位会社経由」など多重商流の示唆 |

> 技術スタックの合計は **20 点で頭打ち**、最終スコアは **0〜85 点** にクリップされます。

### 1.2 技術者メール (EMS) の品質スコア [上限 70 点相当]

| 項目 | 加点 | 検出キーワードの例 |
|---|---|---|
| 明示ワード | **+15** | 「技術者ご紹介」「人材」「エンジニア募集」など |
| 稼働条件 | **+10** | 「稼働可能」「即日参画」「6月稼働」など |
| 技術スタック | **+3/件** (上限 +20) | Java, Python, React, AWS など (個別技術名) |
| 所属区分 | **+10** | 「正社員」「業務委託」「個人事業主」「フリーランス」 |
| **添付ファイルあり** | **+15** | スキルシート (Excel/PDF/Word) 添付 |

### 1.3 品質スコアによるステータス分類

ステータスは **案件メール (PMS = `project_mail_sources`) と技術者メール (EMS = `engineer_mail_sources`) の `status` カラム** に記録されます。元の Email テーブル (`emails`) には記録されません (Email は単なる受信メールで、案件/技術者として認識できたものだけが PMS/EMS に展開されます)。

| 品質スコア | PMS/EMS の `status` | 画面での扱い |
|---|---|---|
| **60〜** | `new` (新規) | 「新規」一覧 (`/matching` `/engineer-mails`) に表示・対応推奨 |
| **40〜59** | `review` (要確認) | 「要確認」一覧に表示・情報不足だが目を通す価値あり |
| **30〜39** | `review` または `excluded` | 一覧表示はステータスに従う。**鮮度マッチング機能の対象**には含まれる (`FreshMailMatchingService` の品質下限 30) |
| **0〜29 / 除外判定** | `excluded` | 一覧表示なし・鮮度マッチング対象からも外れる |

> 「除外判定」は単純に低スコアだけでなく、「営業メール」「無料セミナー案内」など案件・技術者として認識できない明らかなノイズメールも含まれます (`ProjectMailScoringService::isExcluded()` で判定)。

## 2. マッチスコア (案件 × 技術者の相性評価)

「この案件にこの技術者は合うか?」を **100 点満点で評価** します。マッチ候補カードに表示される **大きな数字** (例: `◎ 82`) はこのスコアです。

### 2.1 5 項目の合計 (100 点満点)

```
マッチスコア = ① 必須条件一致 (40点)
             + ② スキル適合度 (25点)
             + ③ 条件適合度  (20点)
             + ④ 稼働・タイミング (10点)
             + ⑤ 商流・実績補正 (5点)
```

### 2.2 内訳の詳細

#### ① 必須条件一致 [40 点満点] — 案件のハードな条件

| サブ項目 | 配点 | 判定ロジック |
|---|---|---|
| **国籍** | 15 点 | 外国籍OK = 15点 / 不明 = 8点 / 日本人のみ条件で技術者が日本人 = 15点 / **外国籍だが日本人のみ案件 = 0点 (除外)** |
| **年齢制限** | 15 点 | 制限なし = 8点 / 不明 = 5点 / 適合 (例: 45歳以下→40歳) = 15点 / **超過 (例: 45歳以下→50歳) = 0点 (除外)** |
| **勤務形態 (常駐/リモート)** | 10 点 | 案件と技術者の希望が合致 = 10点 / 部分一致 = 5点 / 不一致 = 2〜3点 |

> ★ **国籍と年齢で「除外」になると、その時点でマッチスコアは 0 点** になり、他の項目に関わらず候補に出ません。これが「足切り」です。

#### ② スキル適合度 [25 点満点] — 技術スキルのマッチ度

| サブ項目 | 配点 | 判定ロジック |
|---|---|---|
| **必須スキル** | 20 点 | 案件の必須スキルのうち何件マッチしたか × 20 (例: 5件中3件マッチ → 12点) / スキル情報なし = 10点 |
| **尚可スキル** | 5 点 | 案件の尚可スキルが何件マッチしたか (1件1点 × 上限5) |

> スキル比較は **大文字小文字無視 + 部分一致 + アルファベット正規化** (例: "Java" と "java" は一致、"JavaScript" と "javascript" は一致)。

#### ③ 条件適合度 [20 点満点] — 契約・場所などの条件

| サブ項目 | 配点 | 判定ロジック |
|---|---|---|
| **単価** | 10 点 | 案件単価レンジと技術者希望レンジの **重複率** × 10 (重複なしで差 10万以内 = 3点 / 完全一致 = 10点 / 大幅乖離 = 0点) |
| **勤務地** | 5 点 | リモートOK = 4点 / 都道府県一致 = 5点 / 地域一致 = 4点 / 不一致 = 1点 / 情報不足 = 2点 |
| **契約形態** | 5 点 | 準委任×個人 = 5点 / 準委任×BP = 3点 / 派遣 = 4点 / 情報不足 = 3点 |

#### ④ 稼働・タイミング [10 点満点] — いつ参画できるか

| サブ項目 | 配点 | 判定ロジック |
|---|---|---|
| **稼働状況** | 5 点 | 稼働可能 = 5点 / 稼働予定 = 3点 / 現在稼働中 = 1点 / 不明 = 3点 |
| **開始時期** | 5 点 | 案件開始日 ≧ 技術者稼働可能日 = 5点 / 1ヶ月以内のズレ = 4点 / 2ヶ月以内 = 2点 / それ以上 = 0点 |

#### ⑤ 商流・実績補正 [5 点満点] — 過去取引実績

| サブ項目 | 配点 | 判定ロジック |
|---|---|---|
| **過去取引社数** | 5 点 | 5社以上 = 5点 / 3〜4社 = 3点 / 1〜2社 = 1点 / 0社・不明 = 2点 |

### 2.3 ランクラベルの表示

マッチスコアによってカードに以下のラベルと色が付きます (実装: `rankLabel` 関数 / `engineer-mails/[id]` `matching/[id]`):

| マッチスコア | ランク表示 | 色 | 意味 |
|---|---|---|---|
| **80〜100** | ◎ | 緑系 (`#16a34a`) | 強力マッチ候補 |
| **60〜79** | ○ | 青系 (`#2563eb`) | 普通マッチ |
| **0〜59** | △ | 黄系 (`#ca8a04`) | 弱マッチ (情報不足や条件不一致の可能性が高い) |

> ※ ランクラベル自体は **固定ロジック** (3 段階・上記境界)。実際にカードが画面に表示されるかは §2.4 の **表示閾値** (高 70+ / 中 60+ / 低 50+) によります。デフォルト閾値「高 (70+)」では基本的に ◎ と一部の ○ のみが表示されます。

### 2.4 表示閾値の選択 (鮮度マッチング)

`/matching/[id]` および `/engineer-mails/[id]` の鮮度モードで以下のセレクトを選べます:

| セレクト値 | 閾値 | 用途 |
|---|---|---|
| **高 (70+)** | 70 点以上 | デフォルト・実営業で使う候補 |
| **中 (60+)** | 60 点以上 | 候補が少ない時に閾値を下げて拾い直す |
| **低 (50+)** | 50 点以上 | 母数が極端に少ない案件で総ざらい用 |

## 3. 鮮度マッチング機能 (過去 N 日のメールから候補抽出) のフロー

```
[ユーザー]「過去3日 / 高(70+) / ☐対照表」を選択
            ↓
[Step 1] DB から候補を一次絞り込み (SQL)
   - 受信から N 日以内
   - status != excluded
   - 品質スコア ≧ 30
   - スキル jsonb の重複あり (必須スキルが 1 件でも一致)
   - 単価フィルタ (案件単価上限 ≧ 技術者単価上限)
   - 最大 300 件まで
            ↓
[Step 2] 重複除外
   - 案件側: from_address + 件名 + 顧客名 で同一案件を統合
   - 技術者側: from_address + 氏名 + 所属 で同一人物を統合
            ↓
[Step 3] PHP でマッチスコアを 1 件ずつ計算
            ↓
[Step 4] 閾値 (高/中/低) でフィルタ → スコア降順で表示
            ↓
[Step 5 (任意)] ☐対照表 ON の場合
   - 各候補に対し Claude API で対照表生成
   - 必須要件「×」の候補を一覧から除外
```

## 4. 営業協議で確認したい論点 (たたき台)

開発側から営業部にご相談したい点を整理しました。スコアの **配点バランス** や **足切りルール** に違和感があればご指摘ください。各論点で「現状どうなっているか」は前章に説明しているので、該当箇所への参照を併記します。

### 4.1 配点バランスの妥当性 → ★ **§2.1 / §2.2 を参照**

**現状:** マッチスコア 100 点満点の内訳は ① 必須条件 40 点 / ② スキル 25 点 / ③ 条件 20 点 / ④ 稼働 10 点 / ⑤ 実績 5 点 (詳細 §2.2)

**営業に聞きたいこと:**
- **必須条件 (国籍 + 年齢 + 勤務形態) で 40 点** = 全体の 4 割を占めている。これは妥当か?
- **スキル適合度 25 点** だが、現場感覚で「スキル一致が最重要」であれば配点を上げるべきか?
- **商流・実績補正 5 点** は弱すぎないか? 過去実績の評価をもっと重視すべきか?

### 4.2 足切り (即時 0 点) ルールの妥当性 → ★ **§2.2 ① 必須条件一致 を参照**

**現状:** 国籍不適合・年齢制限超過のいずれかでマッチスコアを **即 0 点** にし、候補から除外している (§2.2 ①の★コメント部分)

**営業に聞きたいこと:**
- 国籍不適合 (外国籍だが日本人のみ案件) で **即 0 点** → 実営業でも候補から外す扱いか?
- 年齢制限超過で **即 0 点** → 案件側の「上限45歳」を 1〜2 歳超えただけでも候補に出さなくて良いか?

### 4.3 単価レンジの判定 → ★ **§2.2 ③ 条件適合度 の「単価」行を参照**

**現状:** 案件単価レンジと技術者希望レンジの **重複率** × 10 点 (重複なしでも差 10万以内なら 3 点 / 差 10 万超なら 0 点 / 情報不足は 5 点)

**営業に聞きたいこと:**
- 単価が合わなくても他の条件 (スキル / 稼働) が良ければ提案するか?
- 重複なしの差 10 万以内に 3 点付くロジックは現場感覚に合っているか?

### 4.4 表示閾値のデフォルト → ★ **§2.3 ランクラベル / §2.4 表示閾値 を参照**

**現状:** デフォルトは **高 (70+)**。中 (60+) / 低 (50+) はセレクトで選択 (§2.4 のテーブル)

**営業に聞きたいこと:**
- 営業の現場運用では「最初に開いた時」にどの閾値で候補が見えるのが自然か?
- 高 (70+) で何件くらい候補が出ると現場で「使える」感覚か?

### 4.5 品質スコアの閾値 → ★ **§1.3 品質スコアによるステータス分類 を参照**

**現状:** 品質スコア 60 以上 = `new` (新規一覧)、40〜59 = `review` (要確認)、30〜39 = 鮮度マッチ候補のみ、〜29 = `excluded`

**営業に聞きたいこと:**
- `review` (40〜59) の案件もチェックしているか? それとも `new` だけで十分か?
- 鮮度マッチング (品質スコア 30+) で「情報量が少ない」案件を拾うことの是非

### 4.6.1 案件・技術者・その他の自動仕分けロジック (2026-05-23 追加) → ★ **§5 補足: EmailClassificationService**

**現状:** メール取込時に件名・本文・添付有無から **engineer / project / other / bounce / self** の 5 カテゴリに自動仕分けする。

#### 仕分け手順 (実行タイミング)

```
[1] IMAP 取込時 (KagoyaMailService::syncMessage)
     ├─ MAILER-DAEMON / 上流スパム判定 → category='bounce' stub を即保存 (本文取込スキップ)
     └─ それ以外 → category=NULL で保存 (本文/添付も保存)

[2] スケジューラから EmailClassificationService::classifyPending()
     ├─ 5 分毎に走り、category=NULL のメールをまとめて分類
     ├─ Postgres UPDATE ... FROM (VALUES ...) で 1 文に集約 (Sentry N+1 回避)
     └─ 結果は emails.category / classified_at / extracted_data.classification_reason に保存

[3] 個別取込 (新着 1 件) → 同じ classify() を即時呼ぶ

[4] ルール変更時 → reclassifyAll() で全件 (登録済を除く) を category=NULL に戻して再分類
     ※ 営業 UI からの再分類ボタンは現在無し (§4.6 参照)
```

#### 分類判定の優先順位 (上から順に評価し最初にマッチしたもので確定)

| 順 | 判定材料 | カテゴリ | 備考 |
|---|---|---|---|
| 0  | 自社ドメイン (`@aizen-sol.co.jp` かつ `outsource@` 以外) | `other` | 社内通知・営業担当の返信。outsource@ は外部ML経由なので除外しない |
| 0.5a | 件名キーワード: `企業向け問い合わせ` / `お問い合わせフォーム` | `other` | **2026-05-23 追加: 営業挨拶/会社紹介** |
| 0.5b | 本文キーワード: `ご挨拶もかねて` / `ご挨拶も兼ねて` / `会社紹介に伺い` / `ご挨拶に伺い` / `ご協業のお付き合い` | `other` | 同上。engineer/project キーワードより先に評価 |
| 1  | 添付ファイルあり | `engineer` | スキルシート PDF 想定 |
| 2  | 件名に `【技術者情報】` | `engineer` | |
| 3  | 件名に `要員募集` / `要員探` / `人材募集` / `人材を探` | `project` | 案件側が技術者を募集している案件 |
| 3.5 | 本文に `対応可能な人材` / `見合う要員様` / `案件のご紹介` 等 | `project` | engineer 本文より先に評価 (逆転防止) |
| 4  | 件名に `人材` / `要員` / `スキルシート` / `経歴書` / `フリーランス` / `ご紹介` 等 | `engineer` | |
| 5  | 件名に `IY＠京王多摩センター` 型 (`/[A-Z]{2,3}＠/`) | `engineer` | 技術者プロフィール慣例の件名 |
| 6  | 件名に `28歳／70万` 型 (`/\d{2}歳.*[\/／]\d{2,3}万/`) | `engineer` | 年齢＋単価の混在パターン |
| 7  | 本文に `弊社要員/技術者をご紹介` / `■氏名` / `エンジニアのご紹介` / `要員情報` 等 | `engineer` | |
| 8  | 件名に `【案件情報】` | `project` | |
| 9  | 本文に URL あり | `project` | |
| 10 | 上記すべて該当せず | `project` | フォールバック |

**例外:** バウンス (category='bounce') は取込時に直接付与されるため、上記の優先順位判定をスキップする (§4.6.2)。

#### 2026-05-23 追加した「営業挨拶/会社紹介 → other」ルールの背景

外部の B2B 営業フォーム経由で `outsource@` 宛に届く「ご挨拶もかねてエンジニアのご紹介可能です」型のメールが、`エンジニアのご紹介` キーワードに引っかかり engineer に誤分類されていた。自社ドメイン除外の直後・他のキーワード判定より先に走らせることで、営業挨拶系をまとめて other に振り分け、技術者紹介と切り分けた。

#### 画面での表示
- `engineer` → `/engineer-mails`
- `project` → `/project-mails`
- `other` → `/emails` の「その他」チェック (2026-05-23 追加)
- `bounce` → 暗黙除外 (§4.6.2 参照)
- `self` → 表示なし

#### 分類根拠の確認方法
`emails.extracted_data.classification_reason` に「どのルールでマッチしたか」が保存される (例: `subject_other_keyword:企業向け問い合わせ` / `body_engineer_keyword:■氏名` / `body_url`)。誤分類報告を受けたら、まずこの値で原因ルールを特定する。

**営業に聞きたいこと:**
- 上記キーワードで誤分類される真の案件/技術者メールがあれば連絡を (随時キーワード調整可)

### 4.6.2 バウンスメール大量流入の対策 (2026-05-23 追加) → ★ **§5 補足: CleanupEmails**

**背景:** outsource@aizen-sol.co.jp が外部ML経由で日次 4,000〜5,600 件のバウンス通知 (Mail Delivery System / MAILER-DAEMON) を受信していた。1ヶ月で 23,000+ 件蓄積し検索ノイズ・ストレージ膨張の原因に。

**対策 (2026-05-23 実装):**
1. **`emails:cleanup` artisan command に Step 0 追加**: `category='bounce' AND received_at < 7日` を毎日 03:00 JST に削除 (dedup anchor は新着取込時のみ参照されるため7日で十分)
2. **`/emails` カテゴリフィルタで bounce を暗黙除外**: チェックがすべて外れた状態でも bounce は隠れる (バウンスを見る必要があれば URL 直打ち `?category=bounce` で可能)
3. **過去分の一括削除**: バッチ削除 (LIMIT 1000 × loop、cascade FK 子テーブル先削除) で本番・ローカル各 23,000+ 件をクリア

**今後の上限見積もり:** 日次 5,000 件 × 7 日 = 35,000 件で頭打ち。

**営業に聞きたいこと:**
- バウンスを見たいケースはあるか? (例: 配信エラーの調査時)
- ある場合は UI からアクセスできるようにすべきか?

### 4.6 「全件再スコア / 全件再抽出」ボタンを営業 UI から外したい → ★ **§5 補足**

**現状:** `/matching` と `/engineer-mails` の管理操作として「全件再スコア」「全件再抽出」ボタンが営業ユーザーにも見える状態 (POST `/v1/project-mails/rescore-all` / `reextract-all` および engineer 版)。

**処理内容:**
- **全件再スコア**: 品質スコア (score / reasons / status) + 抽出情報 (顧客名・単価・スキル等) を全件再計算
- **全件再抽出**: 抽出情報のみ全件再計算 (スコアは触らない)

**ボタンが必要なケース (= 通常は不要):**

| ケース | 頻度 | 営業が押す? |
|---|---|---|
| A. スコアリングロジックを改修した時 | ロジック変更時のみ | ❌ 開発/管理者作業 |
| B. 抽出ロジックを改修した時 (新フィールド・正規表現修正・Excel/PDF パーサ変更 等) | ロジック変更時のみ | ❌ 開発/管理者作業 |
| C. ドメイン信頼度補正の蓄積反映 (提案実績が貯まると `domain:xxx:+20(96%/3052件)` が経時変動) | 任意 | △ あるとよい |
| D. 15分 batch が一時障害でコケた時のリカバリ (lookback=1日 なので翌日になると 15分 batch では拾えない) | まれ | △ |
| E. 過去に例外で score=0 / 抽出空のまま放置されたレコードのリカバリ | まれ | △ |

**営業に聞きたいこと / 提案:**
- 営業オペレーション中にこのボタンを押すことはあるか? (= 普段の運用で必要か)
- 誤操作リスク (数千件処理が走る・本番 DB が一斉更新される) の方が大きいので、**管理者画面に移動 or 営業 UI からは非表示** にしたい
- ケース C のドメイン信頼度反映は別途軽量ジョブを用意したい (`domain bonus` のみ更新)
